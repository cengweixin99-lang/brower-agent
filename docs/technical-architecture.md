# 浏览器 Agent 技术架构

日期：2026-11-13。状态：架构提案，作为后续开发基线；本文描述的目标能力不代表已经实现。

开发拆分、依赖与阶段验收见 [开发计划](development-plan.md)。

产品定位是接受自然语言目标、在真实浏览器中连续操作、允许用户控制并能交付可验证结果的通用 Agent。信息查找、列表筛选、表单填写是同一执行引擎的不同任务，不单独建立研究采集流水线。

采用现有 TypeScript monorepo、React、Fastify、pi、Temporal、PostgreSQL、Playwright。先交付单用户、单会话的真实 Demo，再沿相同协议演进到生产。生产级要求首先体现在明确的权限、状态、失败语义和验证方式，不以增加服务数量衡量。

**产品范围与默认部署模式**

第一阶段使用产品管理的 Chromium，不接管用户日常使用的 Chrome。Demo 在本机运行；内测和生产把浏览器放到隔离的执行环境。连接用户本地浏览器属于未来的执行适配器，需要另行设计本地授权、连接和隔离，不混入第一版。

用户路径是：创建目标 → 查看实际操作 → 在需要时补充信息或批准动作 → 获取结果。暂停、停止、历史、恢复支撑这条路径；界面继续沿用当前 Figma。通用 Agent 不意味着第一版支持所有网站，发布时明确支持场景与已知限制。

**架构总览与进程边界**

| 层         | 模块                                         | 责任与边界                                                                                 |
| ---------- | -------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 产品交互   | `apps/web`                                   | 目标输入、任务历史、执行时间线、带时间戳的浏览器预览、人工介入和结果；不持有浏览器内部令牌 |
| 控制入口   | `apps/api`                                   | 身份与归属校验、任务命令、状态查询、事件订阅、产物访问；不运行模型或 Playwright            |
| 执行编排   | `apps/worker`                                | 托管 Temporal workflows 和 activities，编排决策、动作、等待、恢复和收尾                    |
| 决策能力   | `packages/agent`                             | pi 适配、上下文构建、模型决策、结构化输出和完成判断；作为 worker 内的库运行                |
| 浏览器网关 | `apps/browser-worker`                        | 会话分配、动作准入、执行账本、撤销与清理；提供内部协议，禁止公网直接访问                   |
| 浏览器实现 | `packages/browser`                           | Playwright 会话、观察、元素定位、动作和文件处理；只由浏览器执行侧调用                      |
| 共享领域   | `packages/contracts`                         | 版本化 DTO、运行时 schema、动作和事件协议；无基础设施依赖                                  |
| 授权与预算 | `packages/policy`                            | 目标域名、动作权限、审批和预算规则；由服务端执行，模型没有最终授权权                       |
| 持久化     | `packages/persistence`                       | 事务、迁移、任务状态转换、租约、动作账本、事件和 outbox                                    |
| 凭据与审计 | `packages/credentials`、`packages/telemetry` | 凭据引用、受控解析、脱敏日志、链路、指标和审计                                             |

调用方向：Web → API → 持久化命令 → Temporal 编排 → 决策 activity / 浏览器 activity → 浏览器网关 → Playwright。执行结果通过数据库快照和事件返回 Web。模型提供商只由决策 activity 访问；网页流量只从浏览器执行环境发出。

生产中控制服务、模型 worker 和浏览器沙箱分开部署、独立扩容。浏览器网关是逻辑入口，底层可以从一个本地进程发展为会话路由和沙箱池，不改变 Agent 工具协议。

**必须长期保持的约束**

1. Agent 不导入 Playwright，不通过任意 JavaScript、shell 或直接 CDP 绕过网关。
2. 一个会话同一时刻只有一个有效操作者，Agent 与人工接管不能同时输入。
3. 每个浏览器动作都有稳定 ID、会话归属、授权依据、执行结果或明确的结果未知状态。
4. 收到停止后撤销后续执行权限；旧模型响应、旧 worker 和迟到重试不能启动新动作。
5. 外部网站的副作用无法与本地数据库做原子事务，不承诺外部操作 exactly-once。
6. 前端只展示服务端状态和真实观察，不用定时器模拟任务进度或成功。
7. 密钥、Cookie、完整 profile 不进入模型上下文、事件日志、Temporal history 或 Git。
8. 演进采用增量迁移和版本化协议，不破坏已启动任务的执行历史。

**Agent 决策与 Temporal 编排**

一次运行绑定目标、约束、会话、预算以及模型、提示模板、工具 schema 和策略版本。工作循环如下：

1. `observe`：获取当前标签页、页面标识、交互元素、必要文本及可选截图，生成 observation ID。
2. `decide`：构建有界上下文，调用模型，返回一个动作提议、请求用户输入或完成提议。
3. `authorize`：服务端校验 schema、执行代次、会话、目标域、预算和审批；拒绝或等待不产生浏览器副作用。
4. `execute`：网关登记动作，检查当前页面和元素前置条件，执行一个动作。
5. `record`：保存结果与证据引用，推进检查点；动作失败或页面变化会回到观察。
6. `verify`：对完成提议核对目标与可观察结果，得到成功、部分完成或需要继续处理的结论。

pi 提供模型交互和消息/工具表达，Temporal 提供持久编排。两者不各自运行一个不受对方控制的工具循环。第一版在 `agent` 内封装有界决策适配器，模型提出动作，由 workflow 单独调度执行。具体 pi SDK 接口以仓库锁定版本为准，此处不是声明已经存在某个单步 SDK 方法。

Workflow 只做确定性分支、定时器、信号处理和 activity 调度。数据库、模型、网络、随机值和浏览器 I/O 均放在 activities。以 `runId + stepId` 标识决策，以稳定 `actionId` 标识动作；activity 重试不得生成新的业务动作 ID。

模型结果保存后重试可以复用；若提供商已处理请求但本地尚未记录，仍可能重复调用和计费，需计入预算并限制重试。工作流历史只传递 ID、版本、精简状态和脱敏错误，原始页面、用户敏感输入及模型消息存储为受访问控制的数据引用。使用 continue-as-new 限制历史增长，并保留业务 run ID、检查点与控制命令游标。

上下文包含用户目标、有效约束、当前观察、近期动作和带来源的摘要。历史压缩不覆盖原始证据，也不能删除审批限制和未解决错误。网页文本标记为外部内容，不能覆盖用户目标、系统规则或授予新权限。检测重复动作、页面无变化和连续失败；达到上限时等待用户或结束，而非无限循环。

**浏览器会话与动作协议**

区分四个对象：Profile 是可保存的网站身份资料；Session 是一次持续的浏览器环境；Tab 是环境中的标签页；Run 是持有会话使用权的一次任务执行。Demo 在一次 run 内保持同一个 context，最初只支持临时 profile。跨任务复用登录态在内测阶段引入，明确复用、失效、删除和并发规则。

第一批动作是 navigate、click、fill、select、scroll、pressKey、wait、extract；标签页切换随后加入。所有动作使用 discriminated union 和运行时校验；错误返回结构化分类，例如 stale_observation、target_missing、policy_denied、session_lost、outcome_unknown。不要让上层解析自然语言错误判断是否重试。

| 协议           | 必须携带的信息                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------------- |
| Observation    | session、tab、document 标识，观察 ID/版本、时间、URL、交互元素引用、文本/截图引用               |
| Action request | workspace、run、step、action ID，session、tab，执行代次、观察引用、动作类型、参数引用及截止时间 |
| Action result  | action ID、执行状态、错误分类、前后观察引用、可验证结果与副作用是否确定                         |
| Decision       | 动作提议 / 等待用户 / 完成提议；可展示的简短理由及证据引用，不要求保存模型私有推理              |

元素引用绑定观察、frame 和文档。网关在执行前重新检查目标可定位性、唯一性及必要前置条件；动态 DOM 无法仅靠一个快照版本消除竞态。校验不通过则重新观察，不自动点击一个“看起来差不多”的元素。截图用于补充观察；坐标操作作为后续受限能力，绑定视口、截图和目标验证。

动作风险由意图、目标和参数共同决定，不能按工具名或 HTTP 方法判断。click 可能提交订单，fill 可能触发自动保存，读取页面也可能使用 POST。Demo 对写操作只使用受控测试站点，不把任意真实站点的表单填写默认视为无副作用。

当前只允许 GET、禁用脚本的抓取通道保留为旧采集模式。通用运行时启用网站所需脚本与浏览器网络行为，同时采用单独的出口隔离，不直接删除现有限制后开放任意网络访问。

**状态归属与一致性**

PostgreSQL 保存产品可见状态、授权、命令和动作事实；Temporal 保存编排历史及调度位置；浏览器执行环境保存实时页面状态。三者职责不同，不能把它们当作自动同步的三份任务状态。

领域状态转换集中在 `persistence` 中的事务接口，不允许 API、worker、gateway 随意改写任务 JSON。API 接受用户命令，worker 推进业务状态，gateway 记录会话与动作事实；调用同一套带前置条件的事务规则。

业务事务同时提交状态变化、单调版本、事件以及必要的 outbox。dispatcher 至少一次投递 Temporal 启动或信号，以 command ID 去重；信号用于唤醒，持久化命令用于恢复和补偿。前端通过快照版本和事件序号丢弃迟到数据。

| Run 状态           | 语义                                                               |
| ------------------ | ------------------------------------------------------------------ |
| queued             | 等待执行容量或会话                                                 |
| running            | 正在观察、决策、执行或验证；具体工作用 phase 展示                  |
| waiting            | 等待输入、审批、登录、人工接管或外部结果核实；附 reason 和超时策略 |
| pausing / paused   | 正在到达安全动作边界 / 已停止自动推进                              |
| stopping / stopped | 已撤销新动作权限、正在清理 / 已确认自动执行停止                    |
| completed          | 目标通过验证，结果已保存                                           |
| failed             | 本次运行无法继续，保留部分结果和失败原因                           |

终态不可原地重开；重试创建新的 run 并关联原 run。审批拒绝默认结束本次运行并记录原因，除非用户明确给出替代目标。等待超时、预算耗尽使用明确原因结束或进入用户等待，不伪装成功。

暂停在动作边界生效，保留中间结果；长期等待可释放计算资源，但保存恢复所需引用，重新获得会话后必须观察。Demo 可以保留唯一会话，内测阶段需要空闲 TTL 和容量策略。

停止接受事务递增 run 的执行代次并写 stopping。网关动作准入和停止操作在会话维度串行化；旧代次请求被拒绝。已经准入的动作视为在途动作，发起取消并记录最终事实；停止无法撤回已发送给网站的请求。只有确认执行已停止或沙箱已销毁并隔离后，才进入 stopped。网络分区时不只凭租约过期重新分配同一 profile，防止旧执行环境继续操作。

Temporal cancellation 是协作机制，不能代替网关撤销与清理。长活动需 heartbeat，并显式选择是否等待取消确认；这一点依据 [Temporal TypeScript cancellation 文档](https://docs.temporal.io/develop/typescript/workflows/cancellation)。

**数据模型与产物**

| 对象                     | 主要字段和用途                                                       |
| ------------------------ | -------------------------------------------------------------------- |
| Workspace / User         | 数据归属、角色和配额；Demo 固定本地 workspace，公开部署前实现鉴权    |
| Task                     | 用户目标、约束、验收要求、创建者；不以 URL 列表作为通用任务模型      |
| Run                      | task、状态、phase、版本、执行代次、预算、会话及配置版本              |
| Step / Decision          | 观察引用、决策记录引用、模型用量、耗时与检查点                       |
| Action                   | 动作 ID、类型、参数摘要/受控引用、审批引用、执行代次、执行状态和结果 |
| Session / Lease          | profile 引用、执行节点、独占持有者、代次、心跳、失效与隔离状态       |
| Observation / Artifact   | 页面或文件类型、对象位置、完整性信息、归属、保留期限                 |
| Approval / UserInput     | 请求内容、绑定动作、参数摘要、决定、操作者、有效期限                 |
| Command / Event / Outbox | 幂等键、序号、命令处理位置、投递与审计信息                           |

查询字段使用关系列，扩展的结构化参数使用 JSONB。不要把所有步骤、截图和长文本堆进 tasks.data。所有业务对象带 workspace 归属，关联关系和查询必须校验同一归属，不能只依赖不可猜测 UUID。

产物存储先用本地目录实现，生产换对象存储，业务层通过统一接口访问。先写临时对象、完成完整性校验，再提交可见引用；失败留下的孤立对象由清理任务回收。原始提示、页面文本和截图可能含敏感内容，需要独立访问控制、加密、保留与删除策略，不能当作普通日志。

凭据记录只暴露 opaque reference。具体密钥仅在需要的执行边界解析，模型看到字段用途而非密码值；登录输入、截图、错误详情也要避免泄露。生产密钥由独立密钥管理设施保护，浏览器 profile 加密保存且禁止同时挂载到多个执行实例。

**幂等、恢复与外部副作用**

Action 状态区分 proposed、authorized、executing、succeeded、failed、cancelled、unknown。数据库内的登记和结果提交幂等，不代表外部网站操作幂等。[Temporal 的 activity 文档](https://docs.temporal.io/activity-definition) 明确指出，结果未成功上报时 activity 可能重试，因此动作账本必须覆盖这一窗口。

| 故障                            | 恢复行为                                                         |
| ------------------------------- | ---------------------------------------------------------------- |
| Web 刷新或事件断开              | 获取 run 快照，从事件游标续接，不创建新任务                      |
| API 在提交任务后崩溃            | outbox 重新投递，稳定 run/workflow ID 防止重复启动               |
| 模型调用超时                    | 有限重试并计入成本；使用已保存结果时不再次请求模型               |
| 动作成功但 activity 回执丢失    | 查询同一 action ID，返回已保存结果                               |
| 网页提交后 gateway 在记账前崩溃 | 标记 unknown；检查站点回执、状态或请用户核实，禁止盲目重复提交   |
| 浏览器崩溃                      | 确认旧实例隔离，恢复允许保存的 profile，重新观察并评估能否续作   |
| 数据库不可用                    | 拒绝新动作；在途动作尽力中止并保留待核实事实，不无账本运行       |
| Temporal 不可用                 | API 接受并保存允许的命令，任务等待；停止通过网关撤销通道继续处理 |
| 执行节点分区                    | 等待隔离确认，不让同一身份出现两个活跃执行者                     |

普通观察可以有限重试；导航和交互仍需检查前置条件；可能产生业务副作用的动作在结果未知时必须核实。不能用统一的“失败重试三次”配置覆盖所有浏览器动作。刷新恢复、编排恢复和浏览器内存恢复必须分别描述，不能承诺恢复未保存的所有表单和 DOM 状态。

**审批、人工接管和安全边界**

服务端策略返回 allow、deny 或 require_approval。授权绑定用户/workspace、网站身份、目标域、具体动作、参数版本、有效期及必要页面前置条件。用户批准后如果目标或参数改变，原审批失效；前端审批按钮不能直接触发 Playwright。

登录、验证码、歧义与敏感提交通过 waiting 状态交给用户。人工接管使用短时、归属校验的控制会话，先撤销 Agent 的输入权限，再授予人工操作；交还时递增代次、重新观察，既有动作提议重新校验。

生产浏览器访问不可信网页，需要非 root、浏览器 sandbox、受限系统调用、资源配额、临时磁盘和网络出口控制。Playwright context 用于会话状态隔离；本产品不把它当作租户安全沙箱。不同用户的执行环境采用独立沙箱；沙箱不能访问数据库、模型密钥或控制平面私网，只通过窄接口交换动作和结果。官方 [Playwright Docker 文档](https://playwright.dev/docs/docker) 区分了可信测试与不可信网页执行，并提示非 root 与 seccomp 要求；不能直接把测试镜像配置当作生产安全设计。

出口默认阻断宿主机、私网和云元数据地址，覆盖重定向、DNS 重绑定、IPv6 和替代网络通道。允许内网站点必须是 workspace 显式配置的独立访问模式。浏览器网络限制落在沙箱和出口层，不能仅依赖页面 route handler。浏览器二进制按受支持版本维护与补丁升级。

下载上传在内测后单独开放：文件归属、大小/类型、路径、恶意内容检查、目标确认和保留期限都进入协议。模型不能指定任意宿主文件路径。服务间使用可轮换身份与认证；本地静态 gateway token 只保留在本机开发模式。

**API 与前端接入**

建议协议分为任务查询、运行控制、事件和产物四类。以下是待实现接口，不代表现有 API 已支持：

| 接口                           | 用途                                                          |
| ------------------------------ | ------------------------------------------------------------- |
| `POST /tasks`                  | 幂等创建目标与首次 run，返回任务和运行 ID                     |
| `GET /tasks`、`GET /tasks/:id` | 分页历史、任务和当前运行摘要                                  |
| `GET /runs/:id`                | 权威运行快照和版本                                            |
| `POST /runs/:id/commands`      | pause、resume、stop、提供输入、请求/结束接管；使用 command ID |
| `POST /approvals/:id/decision` | 校验操作者、版本和期限后记录批准或拒绝                        |
| `GET /runs/:id/events`         | SSE；事件 ID 支持断线续传，历史截断时要求重新取快照           |
| `GET /artifacts/:id`           | 鉴权后读取产物或返回短时受限访问地址                          |

Demo 可以继续使用现有轮询；先稳定事件格式，内测再接 SSE。SSE 传结构化事件与产物引用，不传连续截图二进制；实时画面和交互接管后续使用独立受控通道。跨页状态来自同一 run 快照，截图显示采集时间，断线和等待不能展示成仍在正常执行。

**部署、可观测性和运维**

| 阶段 | 部署方式                                                         | 资源策略                                                   |
| ---- | ---------------------------------------------------------------- | ---------------------------------------------------------- |
| Demo | 本机四应用、现有 PostgreSQL 和 Temporal 开发服务、本地产物       | 固定本地用户、单会话、单活跃任务，其他任务排队             |
| 内测 | 独立测试环境、正式 Temporal 服务或托管服务、对象存储、隔离浏览器 | 少量用户，workspace 配额、会话调度、超时清理、密钥管理     |
| 生产 | API/worker 无状态扩容、独立沙箱池、数据库备份恢复、对象生命周期  | 按浏览器槽位和模型限额准入，租户公平性、节点排空和容量告警 |

Temporal start-dev 不作为生产服务。暂不增加 Kafka、Redis、向量数据库或微服务；outbox、事件和配额先由 PostgreSQL 支撑，只有量化瓶颈出现后再引入额外设施。

日志与 trace 统一携带 workspaceId、taskId、runId、stepId、actionId；不默认记录完整 prompt、Cookie、正文或表单值。关键指标包括任务验收成功率、人工介入率、动作失败分类、结果未知次数、停止确认延迟、排队时间、单任务模型成本、浏览器内存及泄漏会话数。

预算包含最大步骤、模型调用/token、单次与总耗时、产物大小、重试和并发。调用前预留额度、调用后结算；金额依赖配置的价格版本，仍用硬步骤和 token 上限兜底。预算校验属于服务端执行路径。

生产发布前需要真实负载基线、备份恢复演练、密钥轮换、孤儿会话清理、事故告警与手册。SLO 根据内测数据确定；Demo 的低延迟表现不能直接当作生产 SLA。升级先灰度到内部 workspace，旧 workflow 保留兼容 worker；回滚不破坏正在执行的动作账本和数据库兼容性。

**从 Demo 到生产的交付阶段**

| 阶段         | 交付范围                                                                                | 退出条件                                                                            |
| ------------ | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| D0 架构基线  | 通用协议、状态转换、预算默认值、受控网站 fixtures 与验收用例                            | 明确每类状态的写入者、每个动作的重试/审批语义；保留旧采集回归                       |
| D1 真实 Demo | 单用户/会话、持续 context、基本观察和动作、有界模型决策、真实步骤与结果、停止和刷新恢复 | 同一引擎完成信息查找、列表筛选、测试表单填写；无需为每个任务写专属执行流程          |
| D2 可用内测  | 登录 profile、多标签页、审批、人工接管、崩溃恢复、鉴权和基本隔离                        | 受支持网站可稳定完成；暂停/停止与审批竞态通过故障注入；不存在越权和重复提交已知缺陷 |
| D3 生产发布  | 沙箱池、租户配额、正式基础设施、成本与审计、备份、灰度、容量与安全验证                  | 达到冻结评测集门槛并完成恢复/隔离演练，关键安全与一致性用例全部通过                 |

D1 明确不包含真实站点的付款、发送消息、发布或不可逆提交；用受控表单验证操作能力。目标网站先限定到评测覆盖范围。D1 仍然真实调用模型并操作浏览器，测试默认用确定性模型替身，付费模型运行显式开启。

第一批验收用例及建议 Demo 门槛：

- 三种场景各 10 个受控任务：找指定事实并给出处；筛选列表并打开正确详情；填写表单并停在提交前。固定模型、提示和工具版本，显式开启真实模型评测后每类至少通过 8/10；此数字是首轮建议门槛，不是已测成绩或生产承诺。
- 自动化不变量全部通过：stop 后无新动作、刷新不重启任务、旧观察拒绝执行、动作 ID 去重、超预算停止、敏感提交被拦截、等待状态跨页一致。
- 故障注入覆盖 API/worker/gateway 在动作前后重启、活动回执丢失、租约过期、停止与完成竞态、浏览器崩溃和断线续接。通用循环接入的同时维护这些测试，不留到生产前才补。
- 结果通过页面状态、结构化提取、受控站点服务端记录等证据验收。模型自评只作辅助，不能单独判成功。

生产评测另包含受支持真实网站、动态页面、弹窗、iframe、登录过期、拒绝审批、恶意页面指令和会话隔离。记录分场景成功率、成本与人工介入率，不用一个平均成功率掩盖高风险失败。

**现有代码的迁移方式**

1. 现有 URL 采集接口、数据和 workflow 作为旧版本保留；当前实现事实仍以 `architecture.md` 和 `task-execution.md` 为准。
2. 在 contracts 新增版本化通用协议，persistence 通过显式迁移新增 run、step、action 和 observation 等结构。旧 sources 可以展示为旧任务产物，不要求一次性重写历史数据。
3. 将浏览器具体操作从 browser-worker 的 main 拆入 browser 包。新增会话和动作端点，旧 `/read` 继续服务旧任务。网络模式明确分开。
4. 新增通用 workflow 类型和决策 activity；按任务执行版本路由，不能就地替换旧 workflow 的循环逻辑。先通过脚本式工具调用测试会话连续性，再接模型。
5. Web 通过适配层同时展示旧采集任务和新 run；逐步接入步骤、等待原因与产物，不重做一轮视觉原型。
6. 新流程达到 D1 门槛后默认用于新任务，再逐步停用旧任务创建入口；保留旧任务读取及必要的运行兼容。

实现顺序固定为：通用协议与状态 → 持续浏览器会话和动作 → 有界 Agent 循环 → 前端贯通和 D1 验收 → 内测可靠性及生产能力。每一步是可运行、可验证的增量，停止与恢复随新执行路径一起接入。

**暂缓的扩展**

多 Agent 协作、自动生成任意脚本、技能市场、定时任务、团队流程、全网无约束操作、本地 Chrome 接管和跨设备控制，均不属于 D1。保留工具、执行适配器和存储接口即可，不预先建设完整平台。发布地域、数据保留期限、真实并发规模和第一批登录网站需要在内测前确定，不阻塞当前 Demo 开发。
